# 场景 01 · 简历设计与初筛

> **第一性原理**：简历是招聘链路的第一道关，也是求职者用 AI 包装成本最低、最普遍的一关。
> 我们要的是真才实学；简历阶段最该挖的是**技术栈真实性、量化指标真实性、经历一致性**。
> 三条都在简历关上被"光鲜化"——AI 用一个下午，就能把一段没做过的经历写得项目扎实、指标完备。

**对应引擎能力**：`normalize_claims`(简历→结构化断言) / `trap_tactics`(坑题战术) /
`detect_contradictions`(跨断言矛盾) / `detect_signals`(注水信号)。

---

## 技法 ①：AI 注水简历（项目经历/职责被 AI 生光）

- **问题（issue）**：项目经历、职责描述被 AI 写成"体系化、全方位、显著"的漂亮话，
  求职者实际参与度很低甚至没有。
- **第一性原理**：真实能力的可验证维度 = **实操参与度**。往里没做过的人，永远答不出
  "我当时具体做了什么、卡在哪"。
- **伪装手法**：职责全抽象（"负责核心模块""主导技术演进"），无一个具体动作；
  术语堆砌（微服务/Docker/高可用/K8s 一应俱全），但都是"听过"不是"做过"。
- **对抗思路**：
  - **识别**：`detect_signals` 的 `over_generalization` / `no_embodied_detail`——职责条
    若全是"通过…提升…"且无主语、无数字，标记。
  - **有效发问**：对简历里每个可验证断言生成坑题（`trap_tactics` 的 A3 决策陷阱）：
    "这个项目的技术选型是你拍板还是团队定的？当时为什么这么选、放弃了什么？"
    真做过的人会讲权衡，AI 注水的只会顺着说"是的，综合考虑了可扩展性和稳定性"。
- **信息对抗多维度**：简历措辞 + 谁定的决策 + 放弃过什么替代方案，三面夹击参与度。
- **输出决策依据**：若连"这段项目是不是你主导做的"都答不出权衡，这条经历的真实参与度存疑，
  是**降级不信**的强信号。

---

## 技法 ②：虚报量化指标

- **问题（issue）**：量化指标（QPS、性能提升、用户数、降本幅度）被放大或编造，
  作为"做过大事"的证据。
- **第一性原理**：可验证维度 = **量化真实性**。指标是"结果"，做过的人知道它怎么来的，
  没做过的一被追问过程就露馅。
- **伪装手法**：指标写得很漂亮但无过程依据（"性能提升 300%""覆盖 100 万用户"），
  说不出瓶颈、口径、A/B 对照。
- **对抗思路**：
  - **识别**：`detect_contradictions` 的 `scale_mismatch`——简历说某量级，回答里却撑不起；
    `detect_signals` 无具身细节。
  - **有效发问**：`trap_tactics` 的 A1 数值陷阱——把指标改成错误但合理的新值：
    "我看你优化后 QPS 到 1800 了，怎么一步步调上去的？"
    真做过会纠正数值并讲增长曲线；虚报指标的会顺着你点头（`classify_answer` 判 echoed）。
- **信息对抗多维度**：指标值 + 增长曲线 + 优化手段 + 如何验证(压测/线上观测)，多维逼问。
- **输出决策依据**：能否讲清指标的真实口径与达成路径，决定这条量化是否可信、是否值得进技术面。

---

## 技法 ③：技术栈堆砌（熟悉 ≠ 用过 ≠ 主导）

- **问题（issue）**：技能列表塞满"熟练/精通"，实际只是用过 demo / 看过文档 / 压根没碰。
- **第一性原理**：可验证维度 = **技术深度**。"熟悉"是不用负责任的说法——真正主导过的
  人，对技术的底层取舍和坑有体感。
- **伪装手法**：技能是"关键词堆砌"，无对应真实项目佐证；一问到某个技术的实现细节就泛化。
- **对抗思路**：
  - **识别**：`normalize_claims` 后看技术栈与项目职责的 `detect_contradictions`（tech_mismatch）——
    简历写主导 Go 架构、项目里却全是 Java 术语。
  - **有效发问**：`trap_tactics` 的 A2 技术细节陷阱——把实现细节改成"看似合理但实际错"：
    "你们当时是把 Redis 持久化当主存储了对吧？" 真做过会纠正，堆砌的会顺着说错。
- **信息对抗多维度**：技术选型理由 + 实现细节 + 踩过什么坑 + 和你团队技术栈的匹配度。
- **输出决策依据**：A2 坑一戳就穿的技术栈，是**不诚信**信号，即便技术本身不差也影响信任。

## 技法 ④：时间线 / 经历矛盾

- **问题（issue）**：简历内外的时间线、技术栈、经历跨度互相矛盾（如跳槽频繁但项目期长得不合理、
  某项目时间与"主导"角色冲突）。
- **第一性原理**：可验证维度 = **一致性**。真经历自洽；AI/人工拼接的简历，字段之间会有裂缝。
- **伪装手法**：改写经历时未照顾全局时间线，或把多个不相干经历的技术缝进一处。
- **对抗思路**：
  - **识别**：`detect_contradictions`（timeline / tech_mismatch / scale_mismatch）跨断言/跨简历与回答比对。
  - **有效发问**：对时间线断层处提问："这段经历只有 3 个月但写到'主导架构重构'，时间够吗？
    当时团队几个人、你负责哪块？" 真经历能自圆，拼的会卡壳（`classify_answer` 判 vague/echoed）。
- **信息对抗多维度**：时间线 × 角色 × 技术 × 人数，交叉验证经历自洽性。
- **输出决策依据**：前后矛盾不可自圆 = 简历可靠性整体存疑，需重点进技术面核验或降级。

---

## 简历关小结

> 简历关的对抗目标是**筛掉"注水的简历选手"、把可能有真材实料的人的"可疑点"标记出来**，
> 而不是淘汰任何人。标记出来的矛盾/虚报，正好是进技术面时主攻的坑题素材。
