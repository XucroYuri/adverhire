## 0. 为什么先读这里

这个项目的核心原则只有一条，贯穿所有决策：

> **先做 Agent 能力，再做壳（壳 = 界面层 / Web 工作台 / 企业管理端）。**

壳是工具，能力是灵魂。招聘测谎的本质，是「对抗性问询质量」——这套 Agent 能不能真的戳穿 AI 代答、验出简历水分。一个漂亮的 Web 界面后面如果问不出好问题、评不真能力，就没有任何价值，反而给"悬浮产品"盖了层精心装修的空房。

所以文档体系的组织逻辑是：**能力引擎优先，接入层殿后**。

## 3. 核心假设速查（详细见 `01-assumptions.md`）

### → 假设 A：先能力后壳
Agent 对抗性能力是本项目唯一的护城河，壳可复用、可外包、可后补。**砍掉所有 Web 界面，Agent 仍然成立；砍掉 Agent，剩一个空壳毫无意义。**

**推论**：
- 前期质量标尺是"单份简历 → 生成核验提纲 → 真人面试官验证有效性"，而非页面美观。
- 壳（Web 工作台 / API）在 Agent 能力经过真实场景验证后再投入。

### → 假设 B：能力内核足够薄
MVP 不依赖 Milvus / RAG / 多 Agent 编排这类重型能力。核心是**提示词策略 + 简历结构化数据 + 问答状态机**。先跑通单进程 CL0 Agent，再用 LangGraph 演进。

### → 假设 C：评估不做"对错"，只做"风险"
五维评估输出的是低/中/高三级风险提示 + 参考依据，**绝不直接生成淘汰结论**。这是产品伦理底线，也是规避"AI 误判"风险的硬约束。

### → 假设 D：护城河在策略库，不在模型
任何 LLM 都能被当作通用引擎使用。真正不可替代的是**对抗性提问方法论 + 分岗策略库 + 实战案例沉淀**——这是系统性工程，不是调 API。

## 4. 反模式（Red Flags）

规划时如果文档开始往这些方向偏，请停下来：

- **壳先行**：先做登录、UI、批量导入、企业配置，把 Agent 能力推到后面。
- **重型堆砌**：为 MVP 引入分布式、向量库、多服务编排。
- **AI 下结论**：评估模型试图直接给出"此人是否应淘汰"。
- **八股题库**：要求候选者"背诵即可作答"的问题——与反 AI 原则自相矛盾。
